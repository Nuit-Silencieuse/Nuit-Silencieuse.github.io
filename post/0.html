1. Presto简介

1.1 概览

Presto是一种用于大数据的高性能分布式SQL查询引擎。Presto是Apache许可证下发布的社区驱动的开源软件。

Presto最初是Facebook为数据分析师设计和开发的，用于在Apache Hadoop中的大型数据仓库上运行交互式查询。在Presto诞生之前，Facebook的数据分析师依靠Apache Hive在他们PB级的数据仓库上运行SQL分析。Hive不适合Facebook的规模，而Presto是为了填补快速查询这块的差距而发明的。最初的开发始于2012年，并于当年晚些时候部署在Facebook上。2013年11月，Facebook宣布将其开源。[^2]

Presto 旨在处理数据仓库和分析任务：数据分析、聚合大量数据以及生成报告。这些工作负载通常被归类为在线分析处理（OLAP）。[^1]

1.2 相关概念

以下内容大部分引用自官方文档，并翻译为中文。[^5]

1.2.1 Server Types

Presto 服务器有三种类型：Resource Manager、Coordinator、Worker。以下部分将解释它们之间的区别。

Resource Manager：聚合所有Coordinator和Worker数据并构建集群全局视图的服务器。采用分离式Coordinator的 Presto 安装需要一个Resource Manager。集群支持多个Resource Manager，每个Resource Manager均作为主节点运行。

Coordinator和Worker通过 Thrift API 与Resource Manager通信。

Coordinator

Coordinator：负责接收SQL Query，解析SQL，生成和优化执行计划，生成和调度Task到Worker上。Coordinator将一个完整的Query，拆分成了多个Stage，每个Stage拆分出多个可以并行的Task。[^6]

Worker

Worker：负责执行Coordinator发给它的Task，有部分Task负责到外部存储系统拉取数据，这部分Task会先执行，之后再执行那些负责计算的Task。从上图中可以看到，拉取数据的Task是在右侧两个Worker上执行的，负责计算的Task是在左侧一个Worker上执行的。[^6]

1.2.2 Data Sources[^ 10]

Catalog、schema，table是Presto提供的三级数据管理结构。catalog对应连接器，schema对应一个数据源中的数据库，table对应数据库中的表。

Presto 集群使用基于连接器的架构来处理所有的查询。每个catalog配置使用一个连接器访问一个特定的数据源。数据源在catalog中暴露一个或者多个schema。每个schema包含若干个table(表)，表中的每一行就是多列数据，每一列是不同的类型。

1.2.3 Query-execution-model

Statement

Presto 执行符合 ANSI 标准的 SQL 语句。当 Presto 文档中提到Statement时，指的是 ANSI SQL 标准中定义的语句。在 Presto 中，语句仅指 SQL 语句的文本表示。当执行一个语句时，Presto 会创建一个查询以及一个查询计划，然后将其分发到一系列 Presto 工作节点上。

Query

当 Presto 解析一条语句时，会将其转换为一个查询，并创建一个分布式查询计划，该计划随后在 Presto 工作节点上作为一系列相互连接的阶段执行。

语句（statement）与查询（query）之间的区别很简单。语句可以理解为传递给 Presto 的 SQL 文本，而查询则指为执行该语句而实例化的配置和组件。查询包含stages, tasks, splits, connectors以及其他协同工作的组件和数据源，共同生成结果。

Query Plan

Query Plan以节点树的形式表示，每个节点大致代表一个operator。由于不同查询计划的性能表现可能不同，Presto 使用查询优化器来选择高效的计划。

优化分为两个阶段：逻辑优化和物理优化。逻辑优化阶段仅基于算法复杂度对计划进行转换。经过逻辑优化的查询计划随后被转换为物理查询计划，该计划针对分布式执行进行了优化，并包含诸如应处理查询计划节点的 Presto 服务器的数量和类型，以及数据如何在它们之间交换等细节。

Plan Fragment

Plan Fragment是由不同 Presto 服务器上的任务执行的物理查询计划的一部分。

Stage

当 Presto 执行查询时，会将执行过程分解为一个stage层次结构。例如，如果 Presto 需要聚合存储在 Hive 中的十亿行数据，它会创建一个root stage来聚合多个其他stages的输出，而所有这些stages都旨在实现分布式查询计划的不同部分。

构成查询的stage层级类似于一棵树。每个查询都有一个root stage，负责聚合来自其他stages的输出。stage是Coordinator用来建模分布式查询计划的结构，但stage本身并不会在 Presto 工作节点上运行。

Task

如前一节所述，阶段（stage）用于表示分布式查询计划的特定部分，但stage本身并不会在 Presto 工作节点上执行。要理解stage是如何执行的，你需要了解stage实际上是通过一系列task实现的，这些task分布在 Presto 工作节点的网络中。

任务是 Presto 架构中的“工作核心”。一个分布式查询计划会被分解为一系列阶段，这些阶段再被转换为任务，进而对数据分片进行操作或处理。

Split

Split是并行执行时最小的调度单元。

当 Presto 调度查询时，Coordinator会向连接器查询表可用的所有Split列表。Coordinator会跟踪哪些机器正在运行哪些任务，以及哪些任务正在处理哪些Split。

split描述从底层读取和处理的一段数据，split是任务分配的单元。连接器能够做的操作依赖于底层的数据源。

例如，hive连接器用以下信息描述split：文件的路径、所取数据的offset、length。[^10]

Driver

任务包含一个或多个并行的Driver。Driver处理数据，并将operator组合起来生成输出，然后由任务聚合，并传递给另一stage的另一个任务。Driver是一系列operator实例的集合。可以将Driver理解为内存中一组物理的operator。它是 Presto 架构中最低级别的并行单元。每个Driver有一个输入和一个输出。

1.2.4 其他概念

以下资料大部分来自于ChatGPT。因为需要快速理解大量基础概念，在此仅作简要介绍用，可能含义上有所偏差和错误。

pipeline（operator pipeline）：一连串算子（operators）在同一执行线程或同一任务内顺序执行的处理流，pipeline 内部可通过多线程并行化来提升吞吐。

shuffle / buffered in-memory data transfers（带缓冲的内存数据传输）：为了按 key 将数据从一个 stage 的 tasks 重分布到另一个 stage 的 tasks，引擎会进行 shuffle。shuffle 涉及数据序列化、网络传输、内存缓冲与键重分布，是分布式查询中代价最高的操作之一。

Data Layout Properties（数据布局属性）：指 connector 或节点暴露的关于数据输出的物理特性（例如已经按某列 partitioned 或标为索引），优化器利用这些属性来减少或避免 shuffle。

Data Layouts / connector Data Layout API：由数据源连接器（connector）暴露给引擎的物理数据组织信息接口，例如文件位置（locations）、partitioning、sorting、grouping、indices 等。优化器利用这些物理信息选择更少数据移动或更快访问的计划。

Node Properties（节点属性）：plan 中节点可声明其输出的物理特性（partitioning、sorting、bucketing、grouping），并能声明对下游的 required 或 preferred properties，供优化器在插入 shuffle 时作决策。

required properties / preferred properties：required properties 为必须满足的物理属性（例如某个算子要求数据按某键 partition），preferred properties 为优化器优先满足但非强制的属性。优化器在插入或调整 shuffle 时会尝试满足这些属性。

partition skew（分区倾斜）：数据按分区键分布不均，导致部分节点承载大量数据/计算，其他节点空闲，形成瓶颈与负载不均，从而降低并行效率。

Intra-node Parallelism（节点内并行）：在单一物理节点（worker）内通过多线程并行执行计算以提高利用率，能共享内存状态（如哈希表）并减少网络开销。

join strategy selection：在多种 join 算法（例如 hash join、broadcast（replicated）join、index nested loop join 等）之间选择最合适的一种，依据数据大小、选择性、是否有索引与网络成本等因素。

join re-ordering：改变多表 join 的执行顺序（join order），因为不同顺序会产生不同中间结果大小，严重影响成本。优化器会尝试选择更优的 join 顺序。

2.2 逻辑查询计划

首先我们深入一步探索一下coordinator内部发生了什么事情。当一个SQL语句提交给coordinator的时候，是普通的文本模式。coordinator接收文本，解析并且分析这段文本。然后它创建出一个执行计划。这个工作有是图4-6所描述的。查询执行计划从通常意义上概括了处理数据和返回结果的步骤。

2.3 分布式查询计划

分布式的执行计划扩展了简单查询计划，包含了一个或者多个stage(阶段)。 简单查询计划会分割成计划段。一个stage描述的就是一个计划段(fragment)在执行时刻，包含了stage的计划段中所有的任务。

coordinator分割开整个plan，从而有效的利用集群的并行度加速整体查询的速度。由于有多个stage，导致会出现一个依赖树。stage的个数取决于查询的复杂度。

2.4 Task分配

分布式查询计划定义了定义了stage，以及在Presto集群中执行query的方法。coordinator用它来做进一步的规划、调度task到worker节点上。 一个stage包含了一个或多个task。典型的，会引入很多task，每个task处理一小片数据。

2.5 执行过程

数据源阶段的task以page（页）这种格式生成数据。page是以列式格式存储的多行数据集合。page数据通过stage的依赖关系，流向下游的stage。 不同的stage之间通过exchange运算交换数据，这种Operator从上游的stage中读取数据。

source task使用数据源的SPI来从底层的数据源中获取数据，数据以page的形式流向Presto，流过整个引擎。各个Operator根据自己的语义处理和产生数据。例如filterOperator丢掉一些数据，project运算发产生新的列数据。task内部的Operator之间的顺序成为流水线。流水线上最后一个Operator把他的输出放到ouptut缓存区。下游的exchange Operator从这个缓冲区获取数据。不同worker之间的Operator是并行执行的。

所以，task就是计划段（plan fragment）分配给worker运行时的称呼。当一个task创建出来后，它为每一个split初始化一个driver。每个driver初始化一个流水线的operator，然后处理一个split的数据。一个task可能会使用多个driver，取决于Presto的配置。一旦所有的driver都完成了，数据被传递到了下一层split，driver和任务结束了他们的工作，之后被销毁。

3. Hash Join算法背景

3.1 核心概念

Build / Probe 模型[^8]

Hash Join 以「一侧先构建哈希表（Build side），另一侧遍历并查找（Probe side）」为基本模型。构建侧会把要匹配的列内容组织成哈希索引；探测侧对每一行计算 key 的哈希并在哈希表中查找匹配。该思想是 Presto/Trino 默认的连接实现基础。

分布式 Join 的分发策略（Join Distribution Selection）[^8]

在分布式环境下有两种常用策略，可以由join_distribution_type参数配置：

  • PARTITIONED（hash-partitioned）：按 join key 的哈希对左右表都做重分片（Shuffle），使得任意一对可能匹配的行落在同一 worker 上；适用于两边都较大、需要并行处理的情形。
  • BROADCAST（replicated）：把小表广播到保存左表数据的 worker 上，避免大规模 shuffle，适合右表远小于左表的场景。

底层数据结构（Pages／PagesIndex／PagesHash／LookupSource）
Presto/Trino 采用基于“Page”（一批行的内存页）处理的向量化流程：Build 侧的数据被组织为 PagesIndex / PagesHash（或相应的 LookupSource 实现），提供按 key 快速定位匹配行的位置集合（position list），并支持批量 probe 操作以提高吞吐。

溢写（Spilling）与恢复
当 Build 哈希表或相关内存超出阈值时，系统会把部分分区或页写到磁盘（spill），后续以分区为单位恢复并完成 join（即“先溢写再分区回放”）。Spill 实现与恢复流程对理解大表 join 的行为至关重要。

动态过滤（Dynamic Filtering）[^9]
在某些 join（尤其是高度选择性的 inner join）中，可以在运行时把 Build（通常为 dimension / 右表）发现的 key 值集合下发为对 Probe（左表）扫描的动态谓词，从而显著减少需要探测的行数。

Join 类型与 NULL／多对多逻辑

  • 对于 inner join：只输出匹配对。
  • left/right/full outer 需要记录未匹配的行并在末尾补齐 NULL。实现上通常在 Probe 阶段或后处理阶段对未命中的 Build 行做标记或第二次扫描。
  • 对于 semi/anti join，Probe 逻辑只关心“是否存在匹配”，而非所有匹配行的列合并。
    正确处理 NULL、复杂类型（数组/struct）以及相等比较规则（equals/hash）是实现细节中的难点。

我们可以像使用字符串一样使用 Slice，Presto 为什么选择 Slice 而不是 String：

  • 字符串创建代价昂贵（字符串拼接，StringBuilder等）。

4.3.1 Stage Performance

要了解在执行阶段Stage1发生了什么，就需要知道在Stage1有哪些Presto中的基本算子参与其中，点击执行信息页面的”Stage performance”，选择stage1，我们可以看到stage1相关的operator：

可以看出在执行阶段，这个stage被划分为了3条pipeline，一条pipeline就是一组可以以流水线方式running起来的一组算子，也就是说如果一个pipeline的上游算子(pipeline下方位置)只要有计算结果输出(通常是一个page)，那么其下游算子(pipeline上方位置)可以对这个page进行消费，假设上游算子输出了page1，那么当其还在生成page2时，并不会阻塞下游算子对page1的处理，有点类似于SparkStreaming中的micro batch的流式处理方式。但是如果不是在同一个pipeline中的算子，则不能进行这样的流式作业，这就引出了HashJoin相关的处理逻辑。

Presto的HashJoin中相关的两张表，用来构建HashMap(Presto自己实现的HashMap，在hash值冲突时使用codegen来保障高效的比较，value的存储使用address)的表称为build表；而另外一张表的行会进行遍历，依次在build表的HashMap中进行探测(匹配)，所以这个表一般称为probe表。

因为build表的数据要通过HashMap存储在内存中，保证较低的查找复杂度，为了降低内存开销，build表一般选择为小表，例如上边的date_dim表；probe表则没有内存占用的顾虑，可以从文件中一行一行或者一批一批读出来进行遍历，所以probe表一般选择为大表，例如上边的store_sales表。

数据进入HashBuilderOperator之前已经由LocalExchangeSinkOperator和LocalExchangeSourceOperator完成数据partition，即join key的哈希值相同的数据进入同一个HashBuilderOperator。

4.3.3 使用HashBuilderOperator构建HashMap

这个算子是Hash join的一个非常关键的算子，关于该算子需要特别说明的几点是：

  • 该算子会在内存积攒数据

Presto这种MPP架构以流式处理数据著称，但是当遇到HashJoin时，则不得不进行数据的积攒，而HashBuilderOperator就是一个会不断积攒Page的算子。

  • 会阻塞Probe端算子

由于需要构建完整的hash表后才能开始进行真正的join，因为如果HashMap没有构建完成就去查找，会有数据遗漏的问题，所以在hash表构造完成之后，probe端的算子(LookupJoinOperator)才能开始进行数据处理。

PageHash

在PageHash中几个比较重要的数据结构key、addresses以及positionLinks，这三个数据结构相互关联，要解释清楚这三个数据结构在join时的作用，首先需要了解join的目的：hashjoin时，不管是哪种join类型(inner/outer/semi)，都需要判断一个表中的某个值(特指join key)是否在另外一个表中存在，比较快速的方法就是使用hash来判断，这就需要用到key这个数据结构，但是，当我们发现key值相等值时，我们还需要做两类处理，第一是是否真的原始值就相等，如果原始值不等，那么说明hash冲突了，而要判断原始值是否相等，就是需要借助addresses来从积攒的一大堆数据中读取出原始值来判断；另外一个处理是原始值真的就相等了，那么就需要一个地方来存储这些相等的原始值在那一大推数据中的位置(就是address)，以便在inner join时把这些相等的值快速的找到并读出来，这就需要使用到positionLinks这个数组了。

4.4 Hash Join实现方式

4.4.1 Hash Join类图

上图展示了Hash Join所涉及的类图，其中比较重要的类有以下几个：

1） HashBuilderOperatorFactory/HashBuilderOperator，针对build表构建Hash Table；

2） JoinHash，Hash Table承载类；

3） LookupJoinOperatorFactory/LookupJoinOperator，负责probe表逐行探测；

4） LookupJoinPageBuilder，负责构建输出page。

4.4.2 Hash Table构建

HashBuilderOperator负责对build表构建Hash Table。它的基本流程是：

  1. addInput()时将Page累积在内存中；

  2. finish()时，则创建Hash Table；

  3. 不再阻塞LookupJoinOperator，即LookupJoinOperator可以开始处理。

我们重点讲一下Hash Table的构建。JoinHash中有两个非常重要的类：PagesHash和PositionLinks。

PagesHash的field有：

1） addresses，对page内每一行数据进行地址编码，编码公式为pageIndex << 32 | rowIndex，如有2个page，每个page有2行，则addresses内存放的是0，1，4294967296，4294967297；

2） PageHashStrategy，会将原始的数据保存下来；

3） key数组，可以理解为hash表，根据某行join key计算得到hash值，再将hash值进行hash计算得到一个hash表的offset，如果这个offset上没有值则存放该行的address，例如addresses中1这个地址对应的行计算出offset为6，而这个位置没有被占用，则key[6] = 1；

4） mask，掩码，用于对数组key求offset；

5） positionToHashes，byte数组，根据join key计算hash值，但是只保存低位的byte。

PositionLinks处理的是，当hash值冲突且原始值也相同时，将满足这些情况的数据address使用数组链起来。

4.5.1 HashBuilderOperator的状态转移

这个表格是在站内的这篇文档[^4]的基础上修改而成的。

状态 行为 状态转移 (Next State)
COSUMING_INPUT - 算子处于正常构建阶段，持续接收 build 端输入 Page
- 将行写入 PagesIndex，或触发 spill 将分区写盘
正常获取上游数据并积累到内存中（组织为 PagesIndex，未进行实际hash列生成）		 - 当 finish() 被调用且输入耗尽，其中无吐磁盘过程 → 转到 LOOKUP_SOURCE_BUILT
- 若内存不足，Driver调用startMemoryRevoke()进行吐磁盘过程 → 转到 SPILLING_INPUT
LOOKUP_SOURCE_BUILT 完成 LookupSourceSupplier 对象的构建（但仍未实际发生hash生成），此时也是可以吐磁盘的，因为只有实际生成 LookupSource 实例时读取 PagesIndex，此时操作仍是把原始输入数据吐出、原本构建的 Supplier 置空（但会保留checksum，保证后续使用时重建对象有一致性），状态切换到 INPUT_SPILLED - 若内存不足，Driver调用startMemoryRevoke()进行吐磁盘过程 → 转到 SPILLING_INPUT
SPILLING_INPUT 由内存上报引发的状态切换，表示现在积累在内存中的数据正在异步吐磁盘且未完成。此时如果上游数据可消费，则从上游获得的 page 会被直接吐到磁盘中。 - 吐磁盘完成时状态切换为 INPUT_SPILLED
INPUT_SPILLED 所有上游消费均完成且整体放在磁盘中 - 若LookUpJoinOperator没有读磁盘的请求，则直接→ CLOSE
- 若LookUpJoinOperator需要读磁盘 → 转到 INPUT_UNSPILLING
INPUT_UNSPILLING 当 LookupSource 消费端需要实际数据、必须构建 LookupSource 时，如果此时是 INPUT_SPILLED 状态，就会开始异步从磁盘加载数据并保持该状态 - 读磁盘完成时状态切换为 INPUT_UNSPILLED_AND_BUILT
INPUT_UNSPILLED_AND_BUILT 当 INPUT_UNSPILLING 结束后，当前分区所有输入数据加载到内存，生成 LookupSourceSupplier ，等待 LookupSource 实例化
CLOSE 当前分区 LookupSource 被完全消费，可以关闭算子释放资源

4.5.2 LookUpJoinOperator的普通执行逻辑

Pipeline2是join真正执行的一个pipeline，这个pipeline并不是每时每刻都有数据在流转，而是受到了Driver的驱动逻辑的控制，在Presto中，算子的执行和阻塞逻辑有固定的接口方法，每个算子要实现自己的阻塞和执行逻辑，只要实现这些接口，就可以在Driver的驱动逻辑中运行：

  • void finish() 通知下游算子当前算子不会再有page添加进来，当前算子要做的事就是处理已经接受到的最后这个page
  • boolean isFinished() 当前算子不当没有page添加进来，最后的那个page也已经处理完了，不会再有page输出了。
  • ListenableFuture<?> isBlocked() 当前算子是否被block了
  • boolean needsInput() 当前算子还需要有新的page输入，和上边的 finish() 方法相反

4.5.2.1 LookUpJoinOperator的阻塞状态

从代码段可以看出，这个算子被阻塞的原因就是source端，即hash表有没有构造好，如果没有则返回一个Future，在needsInput()方法中会尝试去get这个future的结果，如果build端没有构造好，就返回empty，如果构造好了，就返回一个LookupSource对象。

4.5.2.3 LookUpJoinOperator的finish状态

所有算子的结束状态分为finished状态和finishing状态，finishing状态是算子对内的一个状态，表示算子正在处理最后一个page的数据，当算子处理完这最后的一个page，状态就可以变为finished状态了，注意，这里是可以变为finished状态，不是一定能变，是否能变还会根据其他的一些条件做判断：

  • 是否在finishing状态

所谓的finishing状态，就是不再需要input page，即算子正在处理最后一个input page，而LookupJoinOperator的finishing是由finish()方法设置为true的。

  • 是否在build的状态

这个比较好理解，如果build端没有构造好，那么也无法开始执行join；但是注意这里是两个判断条件，即使lookupSource已经构造好了，probe也可能为空，probe为空是在一个probe端的page被处理完后被设置的，所以如果probe还不为空，说明上一个probe端的page还没处理完，也是不能开始新的probe端的page的处理的。

如果LookupJoinOperator算子的上游算子finished了，即不会输出任何的page了，那么就会调用LookupJoinOperator算子的finish方法。

这里的finish方法很简单，就是把finishing置为true，标明LookupJoinOperator算子正在处理最后一个page了，此时如果再调用他的needsInput()方法，就会返回false了，其上游算子也就不会再调用getOutput方法了。
